## M0 Skeleton

- Works: Docker stack (`docker/docker-compose.yml`), bench on Frappe 16.56.0, test site `lifeos.localhost` on host port 18000, `lifeos` app installed, front-end scaffold (Vue 3, Vite, Tailwind, frappe-ui 1.2.0) served at `/life` behind login, sidebar and phone tab bar as in the mockups.
- Stubbed: every screen shows a placeholder until its milestone.
- Tests: `lifeos/tests/test_m0_skeleton.py` passes.

## M1 Spaces and permissions

- Works: `Life Space` with members and Read or Write access, roles `Life Admin`, `Life User`, `Life Agent`, `permission_query_conditions` and `has_permission` hooks on every DocType with a `space`, the same checks for `Life Space` itself, helper checks used by API methods. Agents cannot delete, cannot change spaces or settings.
- Tests: `lifeos/tests/test_m1_permissions.py` passes, with an owner, a family member who is only in the shared space, and an agent.
- Not yet covered here: file access and search for a second user (tested in M3 and M8), `review.decide` refusal for agents (M3).

## M2 Data model

- Works: all DocTypes of sections 4, 4a and 4b (32, generated by `scripts/gen_doctypes.py`), the organisation fields and their rules (area and tags from the record's own space, project inside `area` or `also_in`), the shared `Life Index` handler on save, archive and delete, `bench execute lifeos.index.rebuild`, composite and FULLTEXT indexes, validations (last four characters only in the vault, check-in ranges, habit log uniqueness, waiting reason, cycle end date), `[[link]]` parsing into `Life Link`, the `life_space` custom field on `Event`, seed and unseed (`lifeos.seed.load`, `lifeos.seed.remove`). Install creates the `Private` and `Shared` spaces with their areas and check-in dimensions.
- Tests: `lifeos/tests/test_m2_data_model.py` passes.

## M3 Inbox and review

- Works: `inbox.create_item`, `claim_next` (oldest first, 30 minute claim timeout, returns file URLs and the filing context), `submit_result` (field-by-field payload validation, invalid proposals refused and the rest kept, one new tag per item), `fail_item`, `retry`, `review.decide`, `review.decide_all`, `review.update_payload`, `meta.proposal_schema`. Every proposal kind creates its record and links it back to the inbox item. Agents are refused on every decision path. Files are private, originals are never changed, images get one preview of at most 1600 px.
- Screens: Inbox (drop zone, instruction box, lists by status, Retry) and Review (original, transcript with edit, summary, proposals with one-tap area, project, also-in, tag and due-date chips, Edit dialog, Accept all, Reject all). Checked at 1440 px and 390 px against `mockups/02-review-desktop.png`.
- `agent/fake_agent.py` runs the pipeline over HTTP with an API key, with canned results.
- Tests: `lifeos/tests/test_m3_inbox.py` passes (23 tests).
- Untested against a real service: a real agent over MCP. The fake agent uses the same methods over REST.

- Tests: `lifeos/tests/test_m4_tasks.py` passes (11 tests).
- Note: the area page reads `Life Index` for notes, documents, chats, references and the timeline. Open tasks are read from `Life Task`, because the rows need due date and priority.

## M5 Journal

- Works: the 12 Week Year grid (tap to tick, count up for actions done several times a week, week scores, average against the target, actions finished for good or dropped), ticks stored as dated `Life Action Log` rows, the Goals tab across cycles with an area filter, Close cycle (outcome and note per goal, final score, read-only afterwards), Plan next cycle (starts the Monday after, carries chosen goals with their open actions), goal history through `carried_from`, the month plan (goals with priority, done, carry forward, Make task, mindsweep with autosave), habits per month (seven boxes a row, count and percentage, Manage habits for one month, year view, `days_per_week` targets, mid-month add and remove), check-ins with ranges and a line chart per dimension, the Pages gallery and page view with an editable transcript, and the weekly review (score, habits, done and carried tasks, open loops, Decide with three buttons, what the job archived with Undo, notes saved as a Life Note under Reviews).

## M6 Calendar

- Works: `calendar.get` merges core `Event` records (repeats expanded by core's own `get_events`), important dates repeated every year (29 February falls on 28 February outside leap years), task due dates and vault expiry dates. `calendar.year` gives the year view: important dates, all-day and multi-day events on each of their days, document expiries and cycle start and end, with timed meetings left out. `calendar.add_event`, `calendar.delete_event`, `calendar.add_important_date`. Events carry `life_space`; an event created by an agent in a space is visible to the owner and hidden from users outside the space.
- Screen: month, week, agenda and year views, a day side panel with Add event and Add important date, previous and next, the year view as in mockup 07 (weekends tinted, today outlined, a bar on days inside the active 12 Week Year), and a list by month at phone width. A one-line prompt shows when Google Calendar is not connected.
- Tests: `lifeos/tests/test_m6_calendar.py` passes (7 tests).
- Untested against the real service: the Google Calendar connection. When the user has an enabled `Google Calendar` record with a refresh token, new events are saved with `sync_with_google_calendar` and that calendar, which is what Frappe's integration pushes. Events pulled from Google take the default space of the user who owns them (tested with a plain insert, not with a real sync).

## M7 Library and Vault

- Works: the Library (notes in a tree under area and parent note, a reader in a reading typeface with the line capped near 70 characters, a CodeMirror 6 Markdown editor with a live sanitised preview, autosave two seconds after typing stops, earlier versions from Frappe's versioning with restore), `[[Title]]` links (a picker opens on `[[`, links are resolved to records on save and stored in `Life Link`, missing targets render muted and are not stored, a rename rewrites the link text in records that point to it, two records with one title are told apart by `[[Title#id]]`), a backlinks panel on notes, tasks, inbox items, projects, goals and vault documents, the Vault (by holder, expiry badges here and on Today, a file viewer, last four characters only), the chat log (`chats.log` for agents, `chats.report` grouped by day, area or project, counts by area, the week's open items with Make task and Close), the daily archive job, `archive.set`, `archive.restore`, the Archive screen, and Undo in the weekly review.
- Tests: `lifeos/tests/test_m7_library.py` passes (14 tests).
- Known limit: the Library tree loads up to 2,000 light rows (name, title, parent, area) in one call so the tree is whole. Every other list is capped at 100 rows per call.

## How to run the local stack

```
docker compose -f docker/docker-compose.yml up -d
docker exec -d lifeos-bench bash -lc 'cd ~/frappe-bench && bench serve --port 8000'
cd frontend && npx vite build        # rebuild the front end
docker exec lifeos-bench bash -lc 'cd ~/frappe-bench && bench --site lifeos.localhost run-tests --app lifeos'
```
