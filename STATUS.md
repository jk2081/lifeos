## UX fixes, set 2

Everything in `UX_FIXES_2.md` is done. The front end is now built the way Frappe builds its own apps: frappe-ui 1.2.0 for controls, shell, icons and tokens; `@framework/ui` (from `apps/frappe/ui` of the bench, proven on Frappe 16.56.0) for list controls, link fields and DocType forms; our own components only where neither has one. `frontend/COMPONENTS.md` is the rule book for new screens.

- **Step 0 passed.** `@framework/ui` is linked with `link:../../frappe/ui`, built inside the bench container, with one copy each of vue, vue-router, frappe-ui and reka-ui in the bundle (`frontend/scripts/check-singletons.mjs`).
- **Tokens and theme.** The Life OS colour variables, the `[data-theme]` block and the `.bt`, `.inp`, `.ch`, `.pl`, `.cd`, `.ck`, `.sh`, `.mt` classes are gone. `styles.css` is 30 lines: the frappe-ui import, three contrast rules, layout helpers and the reading typeface. Dark mode is frappe-ui's `useColorScheme`.
- **Shell and controls.** frappe-ui `Sidebar`, `MobileNav`, `PageHeader`, `Breadcrumbs`, `Button`, `FormControl`, `Select`, `Checkbox`, `Switch`, `DatePicker`, `Badge`, `TabButtons`, `Tabs`, `Progress`, `Tree`, `Tooltip`, `Avatar`, `Skeleton`, `Alert`, `Dialog`, `BottomSheet`, `KeyboardShortcutsDialog`, Lucide icons. `Ico.vue` is removed. No `prompt()` or `confirm()`.
- **Lists.** Every list screen is one `ListView` on `useListView`, with the library's `Filter`, `QuickFilter`, `SortBy`, `GroupBy` and `ColumnSettings` behind the wrappers in `frontend/src/framework/`. Rows are frappe-ui's `frappe-ui/list` parts. Fetching still goes through `lifeos.api`, whose list methods now take standard Frappe filters, `order_by`, extra `fields` and a `summary`, with every field name checked against the DocType on the server. The short URL parameters of set 1 still work (`frontend/src/lib/filterUrl.js`); other conditions go in `f=`.
- **Remembered views.** `Life View State` holds one saved state per user, screen and space; `lifeos.api.views.get_all` and `views.save` read and write only the caller's rows, and refuse agents. A bare list URL restores the saved view into the URL; a URL with a query wins and becomes the saved view; `open=` is never saved; active filters always show a count and Clear.
- **Other library parts.** Search is frappe-ui's experimental `CommandPalette`; the vault document form is `@framework/ui` `FormLayout`; uploads go through frappe-ui's `FileUploader`. Tried and not adopted, with reasons in `DECISIONS.md`: `DesktopShell` and `MobileShell`, both experimental lists, the experimental `Calendar`, `SettingsDialog` as a whole, `@framework/ui` `FileUpload`, `ActivityTimeline`.
- **Fixed in the last pass:** Enter in the search palette opened nothing; the "x of y tasks done" link in the Projects list was squeezed to no width; a view changed less than a second before a reload was not saved on the server; secondary text and two badge colours from the library were below 4.5 to 1. Smaller ones: the Google Calendar notice was cut to three letters on a phone, section headings with a button sat lower than those without, date fields showed ISO dates, graph links and the current-week box were hard to see in the dark theme.

## Summary

### What works

Everything in sections 3 to 12 of the spec, as listed under each milestone above: spaces and permissions, the data model and index, the inbox and review pipeline, tasks and Today, the Timeline, areas and projects, the journal (12 Week Year, goals across cycles, month plan, habits, check-ins, pages, weekly review), the calendar with its year view, the library with links and backlinks, the vault, the chat log and report, the archive job and screen, search, the graph, Settings, and the PWA manifest.

### What is stubbed

Nothing shows a placeholder. These are smaller than a reader of the spec might expect, and each is in `DECISIONS.md`:

- The week view of the calendar is seven day columns, not an hour grid.
- A starred mindsweep topic is a heading that starts with a star character. There is no star control.
- The PWA has a manifest and icons, so it installs to a home screen. It has no service worker, so it does not work offline.
- Install creates the spaces, areas and dimensions. The seed of section 11 (cycle, goals, October plan, habits) is loaded with `lifeos.seed.load`, not by the install itself.

### What is untested

- **Google Calendar.** No Google account was connected. Events made in the app are core `Event` records with `sync_with_google_calendar` set when the user has a connected `Google Calendar` record, which is what Frappe's integration pushes. Events arriving from Google take the user's default space; this was tested with a plain insert, not a real sync.
- **A real agent.** Hermes and Claude were not connected. The fake agent runs the same methods over REST, and three of them were called once through the MCP endpoint by hand. `agent/SKILL.md` has not been tried with a real model.
- **The live site.** Nothing was installed on or read from the live site. Installing beside Folio is untested; `lifeos` reads and writes no Folio DocType, and all its DocTypes start with `Life `.
- **`bench get-app` from GitHub and `bench build --app lifeos`.** The app was linked into the bench from this folder. The same `yarn install` and `yarn build` that bench runs were tested in a clean copy on Linux.
- **Real phones.** Phone layouts were checked in headless Chrome at 390 px with touch emulation, not on a device. Installing to a home screen was not tried.
- **Real files.** Handwriting photos, audio and large PDFs were stood in for by small generated files.
- **The scheduler.** The archive job and the release of stale claims were run directly and through tests, not by a running scheduler.
- Load timings were taken in-process on the bench, without the HTTP layer.

### Known limits

- Acceptance runs no longer leave records on the test site: they run on `acceptance.localhost` (UX fixes, set 4). `lifeos.localhost` holds the seed and demo data (`lifeos.demo.load`, and `lifeos.demo.load_v4` for sources and wiki pages).
- `tools/acceptance.mjs` and `tools/shot.mjs` expect Google Chrome at its macOS path.

### Install on an existing bench

Frappe v16, Node 20 or newer, yarn. The app must sit at `apps/lifeos` beside `apps/frappe` (which `bench get-app` does), because the front end links `@framework/ui` from `apps/frappe/ui`. Replace `SITE` with the site name and the address with the owner's login.

```
cd ~/frappe-bench
bench get-app https://github.com/jk2081/lifeos.git
bench --site SITE install-app lifeos
bench --site SITE migrate
bench build --app lifeos
bench --site SITE execute lifeos.install.set_owner --kwargs "{'user': 'you@example.com'}"
bench --site SITE execute lifeos.seed.load
bench restart
```

Then: set the time zone to Asia/Kolkata in System Settings, make sure the scheduler and the background workers are running (the chat export import is a background job), raise the upload limit if Claude or ChatGPT exports will be imported (`bench --site SITE set-config max_file_size 1073741824`), and open `https://SITE/life`. For agents, create one user per agent in Frappe, add it to its spaces in Life OS with Settings → People and agents → Members → Add member (which offers the `Life Agent` role if it has none), generate its API key, and switch on Enable MCP in System Settings. `README.md` has the same steps with more detail. Take a backup of the live site before installing.

## Upgrade notes

- The front end compiles `@framework/ui` from `apps/frappe/ui` of the bench it is built on. That package is raw source at version 0.0.0 and can change with any Frappe update. **After any Frappe update, rebuild the front end (`bench build --app lifeos`) and run `node tools/acceptance.mjs` before using the site.** Only the files under `frontend/src/framework/` import it.
