# Decisions

Every place where the build chose a default, or differs from `SPEC.md`, with the reason.

## Defaults from section 15

| Question | Default used |
| --- | --- |
| Cycle start date | 5 October 2026, the first Monday of October 2026. Ends 27 December 2026 |
| Unclear journal items | Seeded as written, with `[?]`: "Generic promotion [?]" and "Read three books [?]" |
| Weekly review time | Sunday 18:00, in `Life Settings` |
| Priority codes | Stored as written (I to IV). Lists sort I first, blank last |
| Family or product | One family on one site. No tenant field |
| Folio | Left where it is. `lifeos` reads and writes no Folio DocType |

## Build environment

- **Docker stack.** `docker/docker-compose.yml` starts three containers: `lifeos-bench` (image `frappe/bench`), `lifeos-db` (MariaDB 11.8) and `lifeos-redis`. Volumes and the network are also prefixed `lifeos-`. Host ports are 18000 (web) and 19000 (socketio). The bench lives in the `lifeos-bench-home` volume, outside the repo.
- **Frappe version.** The bench runs Frappe 16.56.0, the same as the live site.
- **The repo is the app.** The repo root is the Frappe app root (`pyproject.toml`, `lifeos/`), so `bench get-app` works on it. The front end is in `frontend/` at the repo root, which is `lifeos/frontend` when the repo is cloned as `apps/lifeos`. This is the layout other `frappe-ui` apps use.
- **Front-end build.** The repo is bind-mounted into the container at `apps/lifeos`, where a bench keeps its apps, and the front end is built inside the container with `yarn install && yarn build`. `frontend/node_modules` in the container is its own volume (`lifeos-frontend-modules`), so the Linux packages do not mix with anything on the host. On a real bench, `bench build --app lifeos` runs the same `yarn build`. (Until UX fixes set 2 the build ran on the host; see that section.)
- **Built assets are not committed.** `lifeos/public/frontend/` and `lifeos/www/life.html` are produced by the build, as in other `frappe-ui` apps.
- **Test users.** `lifeos.tools.devtools.setup_users` creates three users on the test site. Their password is generated into the git-ignored `.env`.

## Differences from the spec

- **Permissions apply to the owner too.** `Life Admin` can manage every `Life Space` and its members, but sees records only in spaces he is a member of, as section 3 says for every user. The `Administrator` account is not restricted.
- **`Life Area` is a plain parent link, not a Frappe nested set.** The tree is small and per space, and a nested set would add `lft`/`rgt` upkeep for no gain. A loop check runs on save.
- **Area is not forced on direct creation.** Section 4a says area is required once a record leaves the Inbox. Accepting a proposal requires an area. Quick add and direct API creation allow a blank area, so quick add stays one text box; such records show as Unfiled.
- **`Life Task.status` has one more value, `Carried`.** Section 7 says carry forward marks the old task `Carried`, but the status list in section 4 lacks it.
- **Extra fields.** These were needed to implement rules in the spec:
  - `Life Month Plan Habit.tracked_from` and `tracked_until`: the days a habit counts in that month (section 8, habits added or removed mid-month).
  - `Life Month Plan Goal.carried_from`: the row a carried goal came from.
  - `Life Goal Action.done_on`: the day an action was marked Done, so later weeks stop counting it.
  - `Life Cycle.final_score`, `closed_on` and `Life Goal.final_score`: stored by Close cycle.
  - `Life Inbox Item.finished_on` (for the archive rule) and `preview_image` (the 1600 px preview).
  - `Life Project.is_archived`, `archived_on`.
  - `space` on `Life Proposal`, `Life Link`, `Life Index`, `Life Action Log` and `Life Habit Log`, so the same permission hooks cover them.
  - `inbox_item` on records a proposal can create, so every created record links back to its source.
  - `Life Index.status` and `record_owner`, so list screens need no second query.
- **A completed task has two index rows.** The Timeline must show tasks both when created and when completed, so a Done task gets a second `Life Index` row of kind `Task Done`, dated `completed_on`. Search ignores that row.
- **Events.** Core `Event` shows a record to other users only when `event_type` is Public, and controller hooks can only narrow access. So every event with a `life_space` is saved as Public, and the lifeos hooks narrow it to the members of that space. Events without a `life_space` behave exactly as in core.
- **Time zone.** Dates are stored and shown in the site time zone. The test site is set to Asia/Kolkata; the live site should have the same System Setting.
- **Text size.** The mockups use 14 px interface text on desktop and 15 px on phones. The app follows the mockups for interface text; all long reading text (notes, transcripts, summaries) is 15 px or larger.
- **Two seed commands.** `lifeos.tools.seed.load` loads exactly the seed in section 11. `lifeos.tools.seed.load_demo` adds example ticks, tasks, chats and notes so the screens can be checked against the mockups; it is not the owner's data and has its own remove command.
- **Journal pages do not need an area.** Accepting a Task, Note or Vault Document proposal requires an area. A Journal Page is a record by date and often spans areas, so its area is optional.
- **Area page and tasks.** The area and project pages read `Life Index` for every cross-type list. Their open-task lists read `Life Task` directly, since they show due date, priority and project, which the index does not hold.
- **An area page includes its sub-areas.** The Tea & Coffee page shows records filed under Ghatia, Ghillidary and so on, with chips to narrow to one sub-area, as in the mockup.
- **Quick add reads a date word only at the start or end of the title.** "Buy sun screen" and "Fix the Monday report" stay as typed.
- **Week score rules.** A dropped action is not planned in any week. An action marked Done counts as planned up to the week it was finished and not after. Ticks above `per_week` do not count. The cycle average is the mean of the week scores up to the current week.
- **Ticks and dates.** `journal.tick(action, week, count)` keeps one `Life Action Log` row per action per week, dated today when the week is the current one, else the last day of a past week or the first day of a future one. Unique on action and date as the spec asks.
- **Close cycle default outcome.** A goal still In Progress with no outcome given is stored as Not Achieved.
- **Charts.** Check-in charts are small SVG line charts written for this app (two series on one 0 to 10 axis, colours checked for colour-blind separation in both themes). `frappe-ui` charts would add the whole of ECharts for eight sparklines.
- **Habit targets.** A habit's month target is its tracked days so far, scaled by `days_per_week / 7` and rounded. The percentage is capped at 100.
- **Deleting events.** Core `Event` lets only its creator delete it. `calendar.delete_event` lets any person with Write access to the event's space delete it (never an agent), so the owner can remove an event an agent filed. It checks read permission and space membership itself before deleting.
- **Calendar range.** `calendar.get` returns at most 100 days per call. The year view has its own method, which returns only the entries the year pages show.
- **Week view.** The week view lists each day's items in seven columns. It is not an hour grid; Google Calendar remains the place for that.
- **Links: both rules kept.** Section 4b says links point to records and a rename needs no rewrite; section 9 and the tests say a rename updates the link text. The app does both: `Life Link` stores the target record, rendering shows the target's current title, and a rename also rewrites `[[Old]]` to `[[New]]` in the Markdown of records that point to it.
- **Ambiguous titles.** When two records in a space share a title, the picker inserts `[[Title#id]]`, which pins the link to one record.
- **Link targets.** A link can point to notes, tasks, people, vault documents and chat logs as the spec says, and also to goals and projects.
- **Open items become tasks only for people.** `chats.make_task` is refused for agents, in line with section 5.
- **Library tree size.** `library.tree` returns up to 2,000 light rows so the tree is complete; this is the one list method above the 100-row cap.
- **Graph library.** Cytoscape.js (MIT, actively maintained) draws the graph. Linked records are laid out with its built-in force layout; records with no link yet sit in rows underneath so their labels do not overlap.
- **Graph colours.** Notes, people, goals and vault documents each have a colour, checked for colour-blind separation in both themes. Tasks, chats and projects join the graph only when a link touches them, and share one neutral colour. Every node carries its title, so colour is never the only cue.
- **Search covers journal pages too.** `search.query` searches every `Life Index` row: notes, tasks, inbox items with their transcripts, chat logs, vault documents, journal page transcripts, check-in reflections and month plans.
- **Seed on install.** Section 11 says the install creates the seed records. The install creates the structure every site needs: roles, the two spaces, their areas and the check-in dimensions. The owner's cycle, goals, October plan and habits are loaded with `bench execute lifeos.tools.seed.load`, so a second family's site, or a test site, does not start with one person's goals.
- **PWA.** The app ships a web manifest, icons and the meta tags phones need, which is enough to install it to a home screen. It has no service worker. Offline use is not in the spec, and a service worker scoped to `/life` would have to be served from outside `/assets`.
- **Future habit days.** A habit cannot be ticked for a day that has not come. The month count is "days done of days so far", so a future tick gave counts above the target.
- **Load test data.** `lifeos.tools.loadtest.seed` writes rows with bulk SQL. Two fifths are real `Life Task` records with their index rows; the rest are index rows of other kinds whose records do not exist, which is enough for the reads the spec names because they read `Life Index`. Half the rows are in one space, so the timings are for a large space and not for the average one. Timings are medians of five in-process calls.
- **MCP.** The installed Frappe (16.56.0) matches the spec: the server is at `/api/v2/mcp`, and `call_method` takes `method` and `args`. Two details the spec does not mention: MCP is off until Enable MCP is set in System Settings, and the server accepts protocol versions 2025-11-25 and 2026-07-28 only.
- **Two lockfiles.** `frontend/package-lock.json` is what the build used on the Mac. `frontend/yarn.lock` was produced by a clean `yarn install` on Linux, because bench installs with yarn.
- **Acceptance script.** `tools/acceptance.mjs` walks section 13 with a browser and the fake agent. For the archive item it moves two dates back with a direct database write on the test site, since no screen lets a person back-date a task.
- **Settings prompts.** Until UX fixes set 2, Rename and Remove in Settings used the browser's prompt and confirm boxes. They are frappe-ui dialogs now.

## UX fixes, set 1

- **Some Today numbers are not on the phone.** The phone layout of Today, as in mockup 05, leaves out the lines "proposals waiting" and "overdue", the sidebar review count, and shows the week score in the heading. Those doors exist on desktop only; the acceptance check skips them at 390 px.
- **Extra filters set by doors.** To make a list count equal the number clicked, some lists take filters that are not in the fix list: area and project on the Vault, Include archived, completed-date range on Tasks, archive reason and archived-date range on the Archive, and a "Today and overdue" choice in the Due filter. They appear in the filter bar only while they are on.
- **Journal lists still navigate.** Goals, the 12 Week Year grid and the Pages gallery are not in the table of screens to convert, so their links still open the goal and page screens. Goals and journal pages open in the pane from every converted screen.
- **The Library tree still opens the reader page.** The tree is the navigation of the full-page reader. The new list view beside it opens the pane.
- **Stepping through rows replaces the URL entry.** Opening a second record with the pane open, or moving with the arrows, replaces the history entry, so Back always closes the pane in one step.
- **Old links still work.** `/tasks?open=NAME`, `/vault?open=NAME` and `/chats?open=NAME`, written before the pane existed, open the pane.
- **Swipe down starts on the pane header.** The body of the sheet scrolls, so the swipe that closes it is taken on the header only.

## UX fixes, set 2

- **Step 0 passed: `@framework/ui` is used.** Proven on Frappe 16.56.0 (commit `49789a1` of 10 November 2026), with frappe-ui 1.2.0. `@framework/ui` declares `frappe-ui >= 1.0.0-rc.1` as a peer and Frappe's `ui/yarn.lock` pins no frappe-ui version, so 1.2.0 stays, pinned exactly. A throwaway page with `useListView`, `Filter`, `QuickFilter`, `SortBy`, `GroupBy` and `ColumnSettings` on `Life Task` and on `Life Index` built, rendered at 1440 px and 390 px with no horizontal scrolling, and produced wire filters and an `order_by` string. `frontend/scripts/check-singletons.mjs` confirms one copy each of vue, vue-router, frappe-ui and reka-ui in the bundle.
- **One `package.json` for both places.** `"@framework/ui": "link:../../frappe/ui"` only resolves when the front end sits at `apps/lifeos/frontend`. The Docker bench used to reach the repo through a symlink to `/workspace/lifeos`, which broke the link, so the compose file now mounts the repo at `apps/lifeos` itself. The Python path file of the editable install was pointed at the same place.
- **The build moved into the container.** `frontend/node_modules` there is the volume `lifeos-frontend-modules`. `frontend/package-lock.json` is gone; `yarn.lock` is the one lockfile, since bench installs with yarn. This replaces the "Two lockfiles" entry above.
- **Tailwind scans `@framework/ui` through the link** (`./node_modules/@framework/ui/src/**`), leaving out its stories and tests. Without this its controls render without icons and spacing.
- **`DesktopShell` and `MobileShell` are not used; `Sidebar` and `MobileNav` are.** The two shells move scrolling from the window into an inner element. The app relies on window scrolling: the router keeps a list's scroll position when the pane opens and closes, and Back restores it. So the shell is our own flex layout holding frappe-ui's `Sidebar`, `SidebarHeader`, `SidebarItem`, `MobileNav` and `MobileNavItem`. The phone menu ("More") is a `BottomSheet`.
- **The shell switches at 768 px (`md`), not 800 px.** frappe-ui's breakpoints are used everywhere. The list controls collapse into a Filters button below 640 px, as the brief says.
- **Rows use `frappe-ui/list`, the stable list parts, not either experimental list.** `@framework/ui/experimental/List` always draws a checkbox column, needs a fixed row height and its own scroll area, and has no state for the row that is open in the pane, so it fits neither the pane nor the stacked phone row. `frappe-ui/experimental/ListView` is the older config-driven list that frappe-ui itself is replacing with `frappe-ui/list`. `frappe-ui/list` (`List`, `ListHeader`, `ListHeaderCellSort`, `ListGroup`, `ListRow`, `ListCell`) is what `@framework/ui`'s own list is built on; it has columns by breakpoint and group headings. Its drag-resize and header-sort helpers are taken from `@framework/ui`'s experimental `List` through `src/framework/columnResize.js`.
- **A row is a static row with a stretched button.** frappe-ui's list guide says a row cannot be a link or button and also hold buttons. Our rows hold a checkbox, a count link or a Restore button, so each row is static with one button stretched over it, as that guide describes, and the open row gets the same surface (`bg-surface-gray-3`) the library gives an active row.
- **Short URL parameters and filter conditions.** `frontend/src/lib/filterUrl.js` maps the short parameters of set 1 to wire filters and back, with unit tests in `frontend/tests/`. A condition that a short parameter can say is sent to the server as that parameter, so the list methods' own rules still apply (an area includes its sub-areas and also-in records; `due=overdue` is worked out on the day). Every other condition goes to the server as a standard Frappe filter in `filters`, and into the URL in `f=`.
- **Presets are saved by name, not by date.** `due=overdue` and `expiry=soon` are stored in the saved view as those words. A remembered "overdue" filter therefore means overdue on the day it is opened.
- **"Show done", "Has open items" and "Include archived" stay switches.** They widen a list's default scope and are not a condition on one field, so the library's Filter cannot express them. They are frappe-ui `Checkbox`es beside the library controls, kept in the URL as before, and count as active filters.
- **The library's Group By is a summary table, not headings.** `GroupBy` gives one row per value with counts and other aggregates, as Desk's report view does. It is offered on every list, and its rows come from our own list methods (a `summary` argument) so the space rules and the list's filters apply. The headings a list already had (tasks by due date, chats by day, area or project, the timeline by day, the archive by area) are record headings, which the library's control does not do (its `CONTEXT.md` says so), so they stay, drawn with frappe-ui's `ListGroup`. The grouping is remembered with the view; it is not in the URL.
- **Table columns start from the DocType.** `ColumnSettings` takes its default columns from the fields marked "in list view" on the DocType, so those marks were set to match the old tables (Area added on filed records, Received on inbox items, Target date on projects; `Life Index` shows title, area, project, date and kind). Columns the screen draws itself (a task's checkbox, a vault badge, a project's progress, an inbox item's proposals) are synthetic columns. Project and Goal on the Tasks table are no longer shown by default; they are added from Columns. The list methods take a `fields` argument for the extra columns, validated like the filters.
- **Link pickers show titles.** The DocType generator wrote `show_title`, a key Frappe does not read, so link search returned random ids as labels. It now writes `show_title_field_in_link`. This is a property of the DocTypes, not a field.
- **Link pickers in the filter are not narrowed to the current space.** The library's `Filter` and `QuickFilter` do not pass filters to their link search, so the Area picker offers the areas of every space the person belongs to. Frappe's permission hooks still keep out spaces they do not belong to, and the list itself is always read in the current space.
- **A virtual filter field.** Tags live in a child table, so "Tag" is declared to the Filter as a field the server resolves from the `tag=` parameter. Only "equals" works on it; another operator is refused by the server with a message.
- **Views are saved once per screen and space, read in one call at start-up.** `Life View State` has `user`, `screen`, `space` and `state`. Its permission hooks let a person see and change only their own rows, the owner of the site included; agents have no permission on it and `lifeos.api.views` refuses them. Start-up waits for the saved views for at most 1.2 seconds; after that the copy in the browser is used and the server copy is applied when it arrives, unless the person has already changed the list.
- **On a phone the pane is frappe-ui's `BottomSheet`**, as the brief asks. It is up to 90 % of the screen high with rounded top corners, where set 1 asked for a full-screen sheet. The acceptance check for the phone pane was changed to match.
- **Search is frappe-ui's experimental `CommandPalette`**, fed from `search.query` with client filtering off. It is imported only through `src/experimental/index.js`.
- **Uploads go through frappe-ui's `useFileUpload`** (private by default, attached to the record). The Inbox drop zone stays ours: its files wait until "Add to Inbox" creates the item they belong to, and both libraries' upload components upload at once to a record that already exists.
- **Keyboard shortcuts.** The "g then a letter" jumps are two-key sequences, which frappe-ui's `useKeyboardShortcut` does not have, so the app keeps its own key handler. `KeyboardShortcutsDialog` (opened with `?` or from the sidebar) lists them with `KeyboardShortcut`, through its slot.
- **Colours for drawing.** frappe-ui tokens are `oklch()` values, which Cytoscape cannot parse. `lib/tokens.js` turns a token variable into `rgb()` by painting it on a one-pixel canvas, so the graph follows both themes.
- **frappe-ui's experimental `Calendar` was tried and not adopted for month and week.** Its click hooks and read-only mode would have covered the popover and the new-event modal, but: the date number and "+n" in a month cell and the week's column headers switch to its own Day view with no hook, and we have no day view (a day opens the pane); its weeks are fixed Sunday to Saturday, ours and `calendar.get` are Monday to Sunday; its named colours have no red or neutral, so vault expiries and task due dates would need hex colours; it keeps its own date and view state apart from our routes; and its week view is an hourly grid, where ours lists each day's entries and stacks on a phone. The month, week, agenda and year views stay ours, on token classes.
- **`SettingsDialog` was tried and not adopted as a whole.** It is a modal dialog around a tab set, and its sidebar, panels, header and body only work inside that dialog, so it would turn the `/settings` page into a modal. Its `SettingsRow`, which stands alone, is used for the review and archive settings. Rename and Remove are `dialog.prompt` and `dialog.danger`. The theme switch is `TabButtons` (System, Light, Dark) on `useColorScheme()`.
- **The Library tree is frappe-ui's `Tree`.** Note rows are links drawn in its item slot, since the tree has no link rows or selected state of its own. Branches can now be collapsed. Enter on a row with arrow-key focus toggles it; the link is reached with Tab.
- **The Markdown editor has a toolbar** (bold, italic, heading, lists, quote, link a record), of frappe-ui `Button`s. The brief describes one; the editor had none before.
- **`FormLayout` is used for the vault document form**, through `src/framework/LifeFormLayout.vue`: the fields are drawn from the DocType's meta, bound to our own values and saved with `vault.save`. The holder is now the library's link search. It is not used for events and important dates: their pane has no edit form and `lifeos.api.calendar` has no update method, so a form there would be new behaviour and back-end work. The task pane, review and journal page keep their purpose-built layouts, as the brief allows.
- **`@framework/ui` `FileUpload` was tried and not adopted; frappe-ui's `FileUploader` is used.** The library's own upload sends no doctype, record or field, so it cannot attach a file to a record. With our own transport put in, its dialog still shows a Private or Public switch for each file that we would have to ignore, so the screen could say "Public" about a file stored private. `FileUploader` uploads in one step, private, attached to the record (`components/FileAttach.vue`), which is the fallback the brief names.
- **`ActivityTimeline` was tried and not adopted.** Two of its files import `~icons/lucide/*`, which need the unplugin-icons resolver; it also pulls in the frappe-ui editor and expects a socket for live updates. The server method it reads (`frappe.desk.form.activity.get_activity_timeline`) exists in 16.56. The panes had no history section before, so nothing was removed. This is the "otherwise leave as is" case of the brief.
- **`@framework/ui` is imported by subpath, never from its root.** The root barrel re-exports onboarding and notification components that import `~icons/...` and do not build here.
- **Three text colours are darkened for contrast.** The brief says the token wins and also that no text may be below 4.5 to 1. frappe-ui's own components use `text-ink-gray-5` for secondary text (list group headings, list header cells, inactive tabs and phone tabs, breadcrumbs, avatar initials, key hints), which measures 3.4 to 4.2 to 1 on our surfaces, and its amber and blue subtle `Badge` measure 3.55 and 4.18 in the light theme. Three rules in `styles.css` point those at darker frappe-ui tokens (`--ink-gray-6`, `--ink-amber-9`, `--ink-blue-8`). No colour of our own is introduced. `node tools/screens.mjs` measures every piece of text on every screen and fails on anything below 4.5.
- **Enter in the search palette.** `CommandPalette` puts the keyboard on the first row when the query changes, which is before a server search has answered, so Enter did nothing. `SearchPalette.vue` sends an input event to the palette's field once the results are drawn, which makes the library highlight the first row again. This uses only the field the library renders; if the palette changes, only that function changes.
- **A view changed in the last second is sent as the page closes.** Saving waits a second after the last change. A reload or a closed tab inside that second lost the change on the server, so the other device kept the old view. Pending saves now go out on `pagehide` with a keep-alive request.
- **`/library?view=list` is the Library list with no query.** The Library's Tree and List switch belongs to the page, not to `ListView`, so `view=list` alone restores the remembered filters, like a bare `/tasks`. A count link to every note carries `view=list&all=1`.
- **The acceptance script no longer depends on how much the test site holds.** After many runs the Private space has more than 100 open tasks and more than 20 matches for the transcript word, so three checks that read "the first page" failed. They now ask for this run's records by the run's stamp. Checks that mean "the whole list" open it with `all=1`, since a bare list URL restores the remembered view. The view-state unit test now removes only the rows it made, where it used to delete every saved view of the three test users.
- **Phone width is checked against the device, not the window.** With phone emulation a page that is too wide enlarges the layout viewport, so `scrollWidth - innerWidth` stays 0 while the fixed tab bar leaves the screen. `tools/acceptance.mjs`, `tools/screens.mjs` and `tools/shot.mjs` now compare with the device width. This found two real cases: the Journal's seven tabs and an area's sub-area switch were wider than a phone. Both now scroll sideways in their own row.
- **The Tasks board heading counts the four columns.** It used to show the number of cards loaded (at most 100), which disagreed with the column counts. It is now their sum, and Show more brings the next cards.
- **Dates in date fields read "15 Nov 2026".** frappe-ui's `DatePicker` shows ISO dates by default; every use passes `format="D MMM YYYY"`, as the rest of the app writes dates. The stored value is unchanged. The vault form, drawn by `@framework/ui` `FormLayout`, keeps the library's own date control.
- **Seen in the screenshot review and left as they are**, because they are the library's look or behaviour that predates this set: link pickers have a darker chevron than selects (two libraries' controls side by side); on a phone the month calendar shows entries as bars without text, and the 12 Week Year grid and the Goals table scroll sideways inside their card; the add button on a phone floats over the last visible row until the list is scrolled; graph labels of closely linked notes overlap, and the graph is too small to read on a phone (the list of links under it is the phone's way in); a wrapped line of row details can end with its separator dot.
- **The acceptance script archives the vault documents of its earlier runs when it starts.** Today lists the 20 documents that expire soonest, and each run adds two.

## UX fixes, set 3

- **One tab bar, `TabBar.vue`, for all three patterns.** It is frappe-ui's `Tabs`, `TabList` and `TabTrigger` in their controlled form (a `model-value`, not route mode), because the open tab is a query parameter and frappe-ui's route mode matches paths. `lib/tabs.js` holds the URL rule (`useUrlTab`) and the `[` and `]` keys.
- **`[` and `]` go to the pane's tabs while the pane is open**, and to the page's tabs otherwise.
- **Changing a pane tab replaces the history entry**, so Back still closes the pane in one step, as set 1 requires. Page tabs and list state tabs add a history entry.
- **State tabs use the values the count links already wrote.** `status=Done`, `status=Waiting`, `status=To Review`, `status=Active`, `expiry=soon`, `open_items=1` and `type=Life Task` each select their tab with no change to the link. The default tab is the absence of the parameter (its own value is accepted too). The new values are `status=loops` (Open loops) and `=all`.
- **Links from before the tabs.** `view=loops` on Tasks is rewritten to `status=loops`. `done=1` ("Show done") is rewritten to the All tab with the condition "Status is not Carried", which is the same list. The "Show done" and "Has open items" switches are gone: the Done, All and "With open items" tabs replace them.
- **"Open" is Open and Doing, on the tab and in every number that leads to it.** Until this set, "open tasks" also counted Waiting tasks. The Open tab leaves them out as the brief says, so the numbers that are doors to the Tasks screen (Today's "Due today" and "Overdue", the open-task counts on Areas, the area page and the project page) now count Open and Doing too; otherwise the number clicked would differ from the tab it lands on. Waiting tasks are on the Waiting tab. Today's own list of due tasks is unchanged and still shows a Waiting task that is due. In the API, `tasks.list(status="open")` is unchanged (Open, Doing and Waiting), so agents see what they saw; the screen asks for the new `status="open_doing"`.
- **Open loops keeps its definition**: Open, Doing or Waiting, no due date, older than 14 days. So a Waiting task can be on both the Waiting and the Open loops tab.
- **Done is the status Done.** Dropped and Carried tasks are under All; `status=Dropped` selects All with that condition.
- **The board on the Open tab has two columns**, Open and Doing; on All it has the four it had.

## Pre-step 6: Frappe conventions

### 1. Whitelisted methods

- **Every whitelisted method takes one HTTP method.** 78 reads are GET-only and 93 methods are POST-only. Over REST, sending a read as POST, or a change as GET, is now refused with 403. MCP's `call_method` picks the right one itself, so agents on MCP see no change. `agent/fake_agent.py` sends its reads as GET, and `agent/SKILL.md` names the reads an agent uses.
- **Five methods that look like reads are POST**, because they can write and Frappe rolls back a GET: `journal.month` (with `create` it makes the month plan), `library.get` (it records when a note was opened), `wiki.rules` and `wiki.overview` (they create the rules page the first time), and `reset.get` (its AI batches record AI usage).
- **The list of GET methods lives in one place.** `scripts/http-methods.py` writes `frontend/src/lib/getMethods.json` from the decorators. The front end's `api()` and the acceptance script send those as GET (objects as JSON, booleans as 1 or 0, empty values left out) and everything else as POST. `test_pre6_conventions` fails if the file is out of date, or if any method lacks `methods` or a type hint.
- **A read that writes now fails loudly on the acceptance site.** `lifeos/web/strict_get.py` runs every GET to a `lifeos.` method in a read-only transaction when the site config has `lifeos_strict_get`. `scripts/acceptance-site.sh` sets it on that site. It is off everywhere else.
- **Type hints accept what callers send.** Lists and objects are `str | list` or `str | dict`, parsed as before, because GET and REST send JSON strings while MCP sends objects. Flags are `bool | int`. Date arguments also accept `date` objects where Python callers pass them. Modules that define their own `list()` use `builtins.list` in hints, because Python 3.14 resolves annotations lazily.
- **Changed test:** `test_ux2_views.test_what_is_saved` now accepts `FrappeTypeError` as well as `ValidationError` for a list passed as a view state. The list is still refused, but Frappe's type check now refuses it first.

### 2. SQL

- **Composed SQL stays, with a reason.** Every interpolated piece of SQL was traced; none came from a caller or the model. Lists build their WHERE from fixed fragments (tab and due maps, the area filter) and columns checked against the DocType meta, with every value a parameter. Rewriting those queries into `frappe.qb` would change working, measured SQL, so they carry `# nosemgrep: frappe-sql-format-injection -- <reason>` instead; `docs/conformance/exceptions.md` lists them, written from the comments by `tools/scan_exceptions.py`. Three queries now need no interpolation, and DocType names written into SQL are checked first (`archive._sync_index`, devtools).

### 3. Manual commits

- **Ask commits once.** The answer so far is kept in the cache for `ask.progress`, not committed to the database while the answer streams. An unexpected failure while answering becomes an error answer ("Something went wrong while answering. It has been logged."), saved with the usage already recorded, instead of a message left "Working".
- **Chat import undoes one bad conversation alone** (a savepoint per conversation). Before, a failure rolled back to the last commit, so up to 24 conversations counted as imported could be lost. Progress is still committed every 25 conversations, but only inside a worker job.
- **The nightly insights job uses a savepoint per space** instead of a commit per space; the scheduler commits at the end.
- **Removed:** the commits in `archive.run_daily` and `index.rebuild` (the scheduler, migrate and `bench execute` commit), in `install.set_owner` and `add_member`, `seed`, `demo` and `devtools` (all run through `bench execute`, which commits). **Kept with a reason:** `after_install`, and the load test's seed and removal.

### 4. Switching user

- **The nightly insights job no longer switches to each space's owner.** It passes the owner to `insights.run(..., user=)`. The AI tools read every record through `permissions.get_doc_checked(..., user=)`, which checks that user's permission (and the Vault rule) without changing the session. AI usage is recorded against that user, and a record the user may not read is skipped, not an error.
- **The chat import job never switches user.** Frappe already runs a queued job as the person who queued it. `chat_import.run` now refuses to run as anyone else, and every chat goes through `chats.log`, which checks that person's write access to the space.
- **Demo data and the load test keep `frappe.set_user`**, with a reason on each line: they act as the owner, the agent or a member on purpose.

### 5. File paths

- **Every read of an original goes through `files.read` / `files.local_path`**, which resolves the File record's real path and refuses anything outside the site's private or public files folder: thumbnails, previews and the chat export import. A `../` path or a symbolic link out of the folder reads nothing (Frappe's own path check let a symbolic link through). The two `open()` calls on pdftoppm's temporary folder carry a reasoned exception.

### 6. Audit fixes (behaviour that changed)

- **A record that only bookkeeping rows point at can now be deleted**: the record a proposal made, an insight's evidence, an Ask thread's scope, an idea's source or target, the source of a wiki change. Before, every task accepted from review was refused with "still used by other records". `org.on_trash` clears those pointers (and removes the insight's evidence row) as part of the delete, so a restore from the trash does not bring them back. Real filing links still block a delete: an idea's area or project, a wiki change's page, a wiki page's cited source. (`ignore_links_on_delete` was tried first and dropped: Frappe applies it to every link of a DocType, so a project an idea is filed under could be deleted and the idea could then not be saved.)
- **Agents no longer see** the sources Vault documents were made from in `inbox.list`, or deleted Vault documents and their sources in `trash.list`, while the space's Vault switch is off. The pages and REST already refused them one by one.
- **Reset's undo trusts only the proposal's name from the browser** and checks the proposal, its item and the record made for the user.

### 7. Review fixes

- **Counts of tasks come from `tasks.total`**, which builds the same WHERE as `tasks.list` (`list_clause`) and only counts. The rule of set 5 still holds: a number and its list are made from one WHERE. Everything else in `counts.py` still calls the list method itself.
- **New indexes** (in `index.ensure_indexes`, and the patch `v6.conformance_indexes` for existing sites): Life Index (space, kind, collection, is_archived, last_opened_on, modified); Life Inbox Item (space, is_archived, status, received_on); Life Task (goal, status); Life Proposal and Life Chat Log (owner, creation). No field changed.
- **An agent's graph leaves out Vault documents while the Vault is closed to it**, also when a link points at one.
- **The load test's full-text timings depend on the index being compact.** On this bench, many seed-and-remove cycles had bloated InnoDB's full-text index until a bare `MATCH` took 135 ms. `OPTIMIZE TABLE` (a rebuild) brought it back to under 10 ms. A real site does not delete 100,000 rows at a time; the load test's numbers in STATUS were taken after a rebuild.

## Set 7: Moving forward

### 1. Key results

- **The goal rule is enforced where a goal is made or its measure changed, not on every save.** The goal dialogs (New goal, the 12-week Add goal) refuse a goal without a finish line or a number. The API `goals.create` applies the rule whenever `measure_kind` is given, and reads a `done_when` without a kind as a milestone; a call with neither is still accepted, as before set 7, because internal paths (the Someday bring back, the project migration, the seed, many earlier tests) make goals without one. Such goals show under "Needs a finish line" in the weekly review and with an amber "Needs a finish line" on Plan > Goals, as the brief says for existing goals.
- **"No reading yet" is `current_on` being empty.** Frappe stores Float columns as NOT NULL with a default of 0, so `current_value`, `start_value` and `target_value` can never be null in the database. A number goal with no confirmed reading has `current_value` 0 and no `current_on`; every screen and rule tests `current_on`. A start of 0 is a real start.
- **Readings carry `suggested_by`** (Agent, Assistant, Owner) beside the fields of the brief, and a `title` for lists. A reading typed by the owner is Confirmed at once. A rejected reading is kept as Rejected, so it never counts; the same value from the same source and day is not suggested twice while one is pending or confirmed.
- **Reading proposals**: `submit_result` stores them at once as Suggested readings and lists them under `readings` in its answer; an item whose only proposals were readings is Done straight away. `Reading` is also a value of the Life Proposal kind list so the schema check stays one list, though no proposal row is written for it.
- **Suggest without a key uses rules**: a number and a unit in the title ("Lose 6 kg", "Ghillidary yield 1800 kg/ha", "Weight 84 to 78 kg" with start and target) suggest Number; anything else Milestone. Years (2026) and "Q4" are not read as numbers. On the acceptance site the fake model answers with the same rules.
- **Make it a habit** creates the habit (or reuses one of the same title) and adds it to the current month's plan with the days a week the words say (daily 7, "3 times a week" 3, weekly or "every Sunday" 1).
- **Mark achieved** closes an annual or open goal as Achieved with its result as the note (an open goal is then archived, as Complete does). A 12 Week Year goal that reaches its target shows "Target reached" and closes with its cycle, since 12 Week Year goals are closed only through Close cycle.
- **Plan > Goals groups by the goal served** through the Order menu ("By the goal served"), which lists goals under "Serves X" headings; the library's Group by on Serves also works.
- **Counted actions were already right.** An action with `per_week` above 1 is ticked one at a time on Today and in the grid, shows "2 of 4 this week", and each tick counts towards the week score (capped at `per_week`). Only a test was added.

### 2. The Outbox

- **`exited_on` and `exited_by`** stand for the brief's `on` and `by`, which are SQL keywords. `record_name` is plain data, not a link, so a record can be deleted while its exit stays. Exits carry a `note` where the backfill had to guess a date.
- **One exit counts per record.** A record that moves from one pile to another (Waiting on someone, then Done) has its earlier exit reversed and the new one recorded, so "out" counts a record once. A record deleted after it had already left (a done task deleted later) keeps its first exit; a record deleted while on the plate is Discarded, and restoring it from the trash reverses that.
- **Delegated** means Waiting on anyone except the space's owner: `waiting_on` that is empty, "me", or the owner's full or first name is not delegation.
- **A capture** is Done when it leaves the Inbox with an accepted proposal, by an intent other than Process (Just keep, Add to wiki), or with nothing to decide; Discarded when every proposal was rejected, or it is deleted; Parked when it was parked as an idea (set 7, step 4). Bringing back the idea it was parked as reverses the capture's Parked exit and records the idea as Done.
- **Saves instead of direct writes.** The hooks only see saves, so three places that wrote a status directly now save the record: an inbox item becoming Done when its last proposal is decided, an accepted proposal being undone (the item goes back To Review), and an open-ended goal being restored from the Archive (its outcome goes back to In Progress).
- **In** counts captures by creation, and tasks, goals and ideas created directly: not from a capture (`inbox_item`, an idea's source), not made from an idea (`brought_to`), not carried (`carried_from`). Deleted records drop out of In; their exits stay in Out.
- **The Outbox's tabs** are the four piles, then "All out" and "Came in", so each of Today's two numbers opens a list with exactly that many rows. The period is a switch (`period=`: this week, this month, 12 weeks). Rows of records that still exist open in the pane.
- **People only.** Life Exit is closed to agents (like insights), and `outbox.*` refuses them; agents never needed it and exits name sensitive captures.
- **The backfill** (`lifeos.patches.v8.outbox_backfill`, last 12 weeks) uses `completed_on`, `someday_on`, a goal's `closed_on`, an item's `finished_on` and the trash's deletion time. Not reconstructable: when a task became Waiting or Dropped, and when an idea was brought back; those exits are dated by the record's last change and say so in their note. Deletions older than the trash's 30 days, and captures parked before step 4, cannot be recovered. Records already reopened leave no exit.
- **Indexes**: `(space, creation, area)` on tasks, goals, inbox items and ideas, and two on Life Exit, keep Today's in-and-out line within the load target (Today under the lens went to 525 ms without them).
- **The acceptance site's demo data** now keeps a read-only Life Project beside each open-ended goal that stands for a project, as the set 6 migration leaves them. A site built from scratch has no projects, and the acceptance checks of old project links need them.

### 3. Working hours and the weekly review

- **The review is one page of four steps**, not a wizard: 1 Score and results, 2 Reset, 3 Goal work for the coming week, 4 Look back, each a section. Reset folds to one line once done or skipped for the week, as before. Steps 1 and 3 show on the current week only, since they are about readings and goals as they are now and the week ahead; older weeks show their score and look back. Step 3 is for people with write access.
- **"The coming week" is the next seven days from now**, not the calendar week after the reviewed one, so a review held on a Tuesday plans the rest of the week and a task added for today shows on Today at once. Slots start on the half hour, inside the working days and hours, and never overlap a timed event or another task with a time; the cards of one review do not overlap each other either. Without a free slot a card offers "No set time".
- **Next action**: the goal's oldest open task (Open or Doing, with no time yet); otherwise the assistant's suggestion (one call for all cards, short model, within the cap, only where Ask is switched on for the space). Without a key the box is empty and the length is 60 minutes.
- **The footer** counts goal work already given a time in the next seven days, plus what is added on the page, against the free working time: working hours less timed events and less tasks with a time that are not goal work.
- **Who**: Me, a person of the space (Life Person, not the one marked Self), or "Someone else…" typed. Anyone but the owner makes the task Waiting on them, which the Outbox records as Delegated.
- **Working hours** are three settings (`work_days`, `work_start`, `work_end`) under Your life > Rhythms, default Monday to Saturday, 09:00 to 19:00. The days are saved in week order.
- **Scheduled tasks** show in Today's Today group with why "Scheduled" and their time, on the rail's timeline (opening the task), and on the calendar as timed items for their length. A task due and scheduled on the same day shows once, at its time. `scheduled_at` and `duration_min` can also be set through `tasks.update`.

### 4. Inbox items left too long

- **Which items**: To Review items, and New items no agent has claimed, received more than N days ago. Items being processed (claimed) and Failed items are never touched; the brief's "Waiting for the agent" is read as claimed and being processed.
- **Accept** accepts the pending proposals as they are; an item with none leaves the Inbox as kept (Done). **Park** makes an idea in Someday from the item (its title, its summary or the start of its text, citing it), rejects its pending proposals, and marks it Done; the Outbox records it as Parked. **Discard** moves it to the trash (30 days). The rules without a key: tasks or dates → Accept; notes only → Park; nothing extracted → Discard; other records → Accept.
- **The batch screen is a dialog on the Inbox** (`?decisions=1`), opened from the banner and from Reset's batch. Confirm selected acts on exactly the ticked items and toasts Undo for a minute. Suggestions are made once per item and kept until it is dealt with.
- **Park and Discard modes** act each night at 05:30 as the scheduler. What they did shows as its own line on Today, not the rhythm banner, so a due weekly review and an automatic clean-up can both show; Undo there brings back everything the rule parked or discarded in the last seven days. Exits written by the rule carry `auto_rule` = old_inbox, which is how that line finds them.
- **Changing the mode** brings its default days (7 for Suggest, 14 for Park and Discard) unless the days were changed by hand.

## Set 8: The weekly review

### 1. The shell, Life Review and the piles

- **The review is not saved until the first change.** `weekly.get` (GET) answers with the review that would start now, computed without writing; `weekly.start` (POST) resumes the Open review or creates it, and sorts the piles (the assistant may be called, within the cap). The screen calls both, so the review reads the same on a site that refuses writes (the owner's site in the read-only acceptance run), where it says "read only" in the header instead of "saved as you go".
- **A review is its reviewer's own.** `Life Review` is filtered to its `user` on top of the space rule, so another member of a shared space neither lists nor opens it. Agents cannot read it at all (it is in `NO_AGENT_DOCTYPES`, like insights and the Outbox).
- **A review locked in the last three days is shown as done** (its done screen) when the review is opened again, instead of starting the next one at once; `weekly.start` with `fresh` starts the next one. An Open review left for a few days covers up to the day it is resumed (its `period_end` moves to today).
- **The period's end is the day of the review**, so a review held on Sunday 22 November covers 16 to 22 November, and the next starts on the 23rd. The header says "Covers … (you skipped last week)" when the period is longer than seven days, and "the last N weeks" for longer gaps.
- **Time spent** is the sum of the gaps between saved changes that are at most ten minutes long, so a review left open over lunch does not count lunch. It is stored as `minutes_spent` at Lock.
- **Which Inbox items are in Library's piles**: items To Review, and New items no agent has claimed for two days (the same items set 7's old-Inbox rule takes; fresh captures waiting for the agent are left alone).
- **Which tasks are in Tasks' piles**: open tasks untouched past the stuck threshold (Reset's rule, `stuck_after_days`, 30 by default), and tasks Waiting on someone other than the owner (as the Outbox defines delegation), in both cases created before the review period started. A task waiting on the owner himself counts only when it is stuck.
- **Keep on a stuck task touches it** (a save sets `last_touched_on`), so it is not stuck again next week; Undo puts the old date back. Keep from Needs you on a stuck task ("This week") also gives it a due date six days out when it has none or it is overdue.
- **Let go on a waiting item marks it Done** ("answered"), which the Outbox records as Done; on a stuck task it is Dropped (Discarded); on an Inbox item it is set 7's Discard (the trash). Park is Someday for tasks and set 7's Park (an idea in Someday) for Inbox items.
- **"Chase" makes a task "Chase <person>: <title>" due today** in the waiting task's area and goal, and touches the waiting task. Undo deletes the chase task permanently, without a Discarded exit (it only existed because of the decision being undone).
- **Undo of a pile** undoes everything the pile settled and every item that was moved out of it, newest first, and puts them back in the pile unsettled, so "Undo restores both". Undo logs are kept in the review's state on the server; the browser only names the item or the pile.
- **A new item that appears after a pile was accepted** (a capture that came in, a task that became stuck) joins its pile unsettled, so the tab is not done until it is settled too. Unsettled items that left the plate elsewhere drop out of the piles.
- **The drawer is our own component on reka-ui's Dialog parts** (`components/ui/Drawer.vue`), as frappe-ui's `BottomSheet` is. frappe-ui's `Dialog` is centred and its layout classes cannot be overridden, and `@framework/ui` has no drawer. `reka-ui` is now listed in the front end's dependencies with frappe-ui's own range (`^2.9.9`), so the lockfile is unchanged and `check-singletons.mjs` still finds one copy.
- **Read only, every tab can be looked at.** Where the review cannot be saved (a site that refuses writes, as in the read-only run on the owner's site), the gates would keep Goals and Reflect closed for ever, since nothing can be settled; there every tab opens, and nothing in them can change anything.
- **Old review links**: `step=reset`, `results`, `goals` and `look-back` (set 7's sections) open the Tasks, Goals, Goals and Reflect tabs. Set 7's review page (`components/journal/WeeklyReview.vue`) is removed.
- **Review notes migrated** (patch `v9.review_notes`): each "Weekly review, 16 Nov 2026" note becomes a Locked review for that Monday-to-Sunday week, owned by the note's author (or the space's owner when Administrator wrote it), with the note's text in `went_well` and `locked_on` at the note's last change. A note whose title does not parse as a date is left alone. The notes themselves stay. Today's weekly review banner is now done once a review covering the week is locked (it was: once the note existed).

## Issue 7: each file stored once, by content, with versions (20 Nov 2026)

- **SHA-256 in a custom field, not Frappe's `content_hash`.** Frappe's `content_hash` is MD5, and Frappe reuses a stored file across the whole site by it. The issue asks for SHA-256 and for no link across spaces, so `File` has a new custom field `life_sha256` (indexed), and a mixin on Frappe's `File` (`extend_doctype_class`, `lifeos.library.files.LifeFile`) reuses a stored copy only inside the record's space, by SHA-256, and only one the uploader can read. Frappe's MD5 is still set and still used by Frappe for files that are not Life OS attachments.
- **"One file, linked to both" is one stored copy with one `File` row per record.** Frappe's `File` belongs to one record (`attached_to_doctype`, `attached_to_name`), and its permissions, downloads and deletes all work through that. So a shared file is one `file_url` on disk, and each record that uses it has its own `File` row pointing to it, which is what Frappe itself does for a copied attachment. Library → Files (#24) can group the rows by `file_url`.
- **A stored copy is deleted only when no `File` row points to it.** Frappe's own check compares MD5s, which two spaces' copies of the same bytes share while their paths differ; the mixin compares paths for Life OS files.
- **The same file sent again to the same record** is caught in an override of `/api/method/upload_file` (`override_whitelisted_methods`), before Frappe's handler runs, because a `File` insert cannot be turned into "use the one already there" from inside. Everything else goes to Frappe's handler unchanged. The override is not open to guests; Frappe's handler is, when the site allows guest uploads. Life OS has no guest uploads. Chunked uploads, `optimize` and `library_file_name` go straight to Frappe's handler without the check.
- **Versions apply only to inbox items with an `external_id`**, as the issue says, and match by the name the file was sent with. To keep that name, a Life OS file keeps the name it was sent with (`file_name`) even when Frappe stores it under a suffixed name (`file_url`). An earlier version stays attached to the item (`life_version_of` names the current row), so it keeps the item's permissions. When the current file is removed, its newest earlier version becomes current. A new version of a photo or PDF drops the preview and thumbnail made from the old one, so new ones are made.
- **Files stored before this change get their SHA-256 from patch `v10.file_hashes`**, so a file sent again after the deploy links to the copy already there. Copies already duplicated stay as they are; merging them is #9.
- **The versions line** ("2 versions, latest 20 Nov") is a ghost `Button` under the file that opens the list of earlier versions, each a link that opens the file. It is on the review (full page and pane) and on the source pane. No mockup covers it.
- **Acceptance 6 is `I7.1440.6` and `I7.390.6`**, one per width as for issue 1. Acceptance 1 to 5 are unit tests, numbered by their position in `test_issue7_files.py`. Titles starting `I7 ` are known to the debris finder.
- **Previews and thumbnails are named after the stored name** (`file_url`), not after `file_name`, because `file_name` now keeps the name the file was sent with, which several files can share. Otherwise the thumbnail of a second `photo.png` was stored as `photo-thumb<suffix>.jpg`.

## Issue 8: one call for an agent to file a piece of work (20 Nov 2026)

- **An input asset is an inbox item.** A reusable input is kept as its own Just keep item, Done at once, with `external_id` = `reusable_as`, which is what `agent/FILE_WORK.md` already asked agents to file by hand. So issue 7's rules apply unchanged (stored once per space by content, a newer file under the same name becomes the current version), the assets an agent filed the old way are found and linked by the same id, and Library → Files (#24) needs nothing new. An asset is looked up by `external_id` whatever its `source_system`, because an id such as `btw-standard-deck` names the asset, not the agent that sent it.
- **Inputs are linked in a child table, `Life Job Input`** (`job_inputs` on `Life Inbox Item`: name, `reusable_as`, `asset`, `file`), not attached as the item's files. An input with no `reusable_as` is used by this job only: its `File` is attached to the job's item, so it keeps the item's permissions, and `files.attachments` leaves out the files `job_inputs` names, so it is listed under Inputs and not under Outputs (nor copied onto an accepted proposal's record).
- **New fields on `Life Inbox Item`:** `job_id` (indexed), `job_inputs` and `job_chat` (the chat log filed with the job). Wiki pages are linked by citing the item (and the chat log) as sources, as wiki pages already link to the items they were written from. The DocType JSON was edited by hand: `scripts/gen_doctypes.py` no longer matches the files it wrote (later sets edited the JSON), so running it would undo their changes.
- **The job's item** is filed with `source_system` (the caller's, `agent` when left out) and `external_id` = `job_id`, so issue 7's versions apply to its outputs, and the item is `Process`, claimed by the caller and To Review while proposals wait (Done when none do). An item filed the old way with the job id as `external_id` is taken over rather than duplicated; that is the "Fixing work filed the old way" path in `FILE_WORK.md`.
- **Filing again:** fields that are sent replace the old values and fields left out keep theirs, as for `create_item` (issue 6). Outputs, inputs and files are never removed. Proposals are matched by kind and payload: one already there is kept whatever its status (a changed preview or confidence is updated while pending), and a pending one that is no longer sent is removed, as `retry` does. Nothing is ever decided.
- **Merging a wiki page:** with no way to merge two texts safely on the server, the caller's text replaces the page's when the caller sends the `base_version` it read (a stale one refuses the whole call), or when this job wrote the page last; otherwise it is added below the page's own text, unless the page already holds it. So the same call twice changes nothing, and nobody's edits are overwritten unread.
- **A Reading is refused in a job.** A Reading is stored at once as a suggested reading, so filing the same job twice would suggest it twice. Readings come from journal photos and notes, not work.
- **`raw_text` (the brief) and `source_system`** are accepted besides the arguments the issue lists, because `FILE_WORK.md` asks for a brief and the item needs a system for its `external_id`. Each input may also carry a `title` (the asset's) and `transcript_md` (its text).
- **One transaction.** Every part is checked before anything is written; the writes then run under a savepoint, and any failure rolls back to it and removes stored copies this call put on disk that no `File` row uses. Over HTTP the request's own rollback does the same. Errors start with the field: `proposals[1]: …`, `outputs[0].file: …`, `wiki[0].content_md is required.`
- **Concurrency:** the lookup by `job_id` is `for update` on its index, so two calls for the same new job do not make two items (the second waits or fails). Two jobs that bring the same new asset at the same moment could still each make it; the lookup by `external_id` alone cannot be locked without locking the space's items.
- **The page:** for a job's item the review's Original becomes **Outputs**, followed by **Inputs** (each input's file with its size and versions, and for a kept asset a "Reusable" badge and a link to it), and a "Filed with it" line linking the wiki pages and the chat log. On a phone the first tab is called **Files**. No mockup covers it; it uses the review's existing parts.

## Issue 9: the tidy command (20 Nov 2026)

- **"The action log" is a log file and a comment per record.** Life OS has no audit DocType (`Life Action Log` holds 12 Week Year ticks), so every change goes to `sites/SITE/logs/lifeos_tidy.log` (Frappe's site logger, at INFO) and as an Info comment ("Tidy: …") on the record it changed, where it shows in the record's timeline.
